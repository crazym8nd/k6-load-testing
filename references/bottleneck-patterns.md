# Паттерны узких мест (bottleneck patterns)

Справочник для диагностики «почему медленно». Каждый паттерн: **сигнатуры → подтверждение →
ремедиация**. Ремедиации ранжированы от дешёвых к дорогим. Все гипотезы — до подтверждения
инфраструктурными данными, трассировками или профилировщиком.

## 1. CPU Saturation (compute-bound)

**Сигнатуры:** p95 растёт с нагрузкой; RPS плато (не растёт при добавлении VU); CPU > 80% на
протяжении прогона; нет утечек/ошибок на низкой нагрузке.
**Подтверждение:** CPU-график коррелирует с ростом латентности; профилировщик показывает горячие методы.
**Ремедиация:** снизить сериализацию → вынести CPU-работу из request-пути → горизонтально
масштабировать → алгоритмическая оптимизация → железо.

## 2. Memory Leak / Heap Exhaustion

**Сигнатуры (soak):** p95 ок первые 30–60 мин, потом деградация; память растёт монотонно; GC
чаще, паузы длиннее; в конце OOM/рестарт.
**Подтверждение:** heap-дампы в разные моменты → растут retained-объекты; RSS растёт после GC.
**Ремедиация:** eviction-политики кэшей → убрать статик-накопители → закрывать стримы/коннекты
в `finally` → тюнинг GC (временный, не фикс) → streaming/lazy.

## 3. Database Bottleneck

**Сигнатуры:** p95 приложения коррелирует с медленными запросами; CPU БД высок при низком CPU
приложения; потоки ждут коннект; ошибки `connection timeout` / `lock wait`.

| Под-паттерн | Индикатор | Причина |
|---|---|---|
| Slow query | БД CPU высок, запросы в slow log | нет индекса, full scan |
| N+1 | число запросов растёт быстрее числа пользователей | ORM грузит связанные по одному |
| Lock contention | lock wait под конкурентной записью | длинные транзакции |
| Pool exhaustion | acquire timeout | мал пул / коннекты не возвращаются |

**Ремедиация:** индексы → батчинг N+1 (eager/`IN`) → сузить транзакции → пул больше (осторожно:
БД имеет свой лимит коннектов) → read-реплики → кэш.

## 4. Thread / Worker Pool Exhaustion

**Сигнатуры:** p95 ок до порога, потом резкий скачок; ошибки 503 / connection refused; очередь
растёт; CPU/память низкие (не compute-bound).
**Подтверждение:** треды активны ≈ max; видно время в очереди до начала обработки (APM).
**Ремедиация:** увеличить пул → найти блокирующий I/O на тредах → async → event-loop → горизонтально.

## 5. Network / Bandwidth Saturation

**Сигнатуры:** латентность высокая даже на малых payload; throughput (байт/с) плато; сеть 100%;
ошибки — connection timeout.
**Ремедиация:** gzip/brotli → пагинация/урезать поля → CDN → апгрейд сети → бинарные протоколы (gRPC).

## 6. Downstream Degradation

**Сигнатуры:** медленный один эндпоинт, остальные ок; ошибки = таймауты к внешнему хосту;
CPU/память здоровы; APM показывает ожидание outbound-вызова.
**Ремедиация:** таймаут на outbound → circuit breaker → кэш ответов → заглушить зависимость в
тесте (WireMock) → SLA с вендором.

## 7. Cold Start / Warm-Up

**Сигнатуры:** первые запросы сильно медленнее steady-state; через 2–5 мин стабилизируется
(«хоккейная клюшка»); сильнее всего на JVM/Python; короткий тест (< 5 мин) даёт завышенные
перцентили.
**Причины по слоям:** JIT-компиляция; открытие TCP/DB-коннектов; DNS; прогрев кэшей.
**Ремедиация:** исключить окно прогрева из оценки SLA → low-load прогрев (10–20% трафика 2–5 мин)
→ readiness-гейт → AOT (GraalVM/Go).

## 8. Event Loop / Async Saturation

**Сигнатуры (Node/Python asyncio/Netty):** латентность резко растёт при низком CPU; `p99 ≫ p95`;
throughput не растёт; тредов мало (async).
**Причина:** блокирующая операция в цикле событий → все остальные ждут за ней.
**Ремедиация:** вынести CPU-работу в worker → async-аналоги блокирующих I/O → async-DB-драйверы
→ дробить большие операции → горизонтально.

## 9. Cache Invalidation Storm (Thundering Herd)

**Сигнатуры:** всплеск латентности/ошибок после стабильности; совпадает с TTL-экспайром / деплоем
/ флашем кэша; много одновременных запросов к одному ресурсу; БД CPU скачет.
**Ремедиация:** lock/mutex на cache-miss → вероятностная ранняя экспирация → stale-while-revalidate
→ jitter на TTL → фоновый refresh.
