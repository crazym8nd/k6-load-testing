# Анализ результата

## Разбор задержки (waiting vs blocked)

k6 собирает разбивку `http_req_duration` по фазам — используй её, чтобы не путать «медленный сервер» с «проблемой соединения»:

| Метрика | Что значит | Сигнал |
|---|---|---|
| `http_req_waiting` (TTFB) | время до первого байта ответа | доминирует и растёт с нагрузкой → сервер очередится/считает (насыщение) |
| `http_req_blocked` | ожидание свободного TCP-слота/keep-alive | высокий → не хватает соединений со стороны k6, а не медленный сервер |
| `http_req_connecting` / `tls_handshaking` | TCP / TLS | высокие → сеть / нет keep-alive |

k6 видит только клиентскую сторону. CPU / heap / GC / пул БД приложения — отдельный поток (см. «Два потока данных»).

## Triage + паттерны латентности

Прежде чем делать выводы о capacity — пройти triage-порядок и классифицировать распределение
латентности. Это не даёт смешать баг, cold-start и насыщение в один «p95 высокий».

### Triage-порядок (всегда в этой последовательности)

| # | Шаг | Что ловит |
|---|---|---|
| 1 | Ошибки | ошибка на низкой нагрузке = баг, не capacity — чинить до интерпретации |
| 2 | Дошёл ли тест до цели | `dropped_iterations > 0` или RPS < RATE → результат частичный |
| 3 | p95/p99 vs SLO | breach или нет на steady-state |
| 4 | Тренд по времени | стабильно / деградирует / cold-start в начале |
| 5 | Per-endpoint | один медленный эндпоинт или все разом (общий ресурс) |

### Паттерны распределения латентности

| Паттерн | Что значит |
|---|---|
| `p50 ≈ p95` (плотный) | стабильно, предсказуемо |
| `p95 ≫ p50` (длинный хвост) | выбросы — GC, lock, холодный кэш, cold-start |
| `p50` растёт с нагрузкой | насыщение — сервер очередится |
| `p99 ≫ p95` | редкие сильные столлы — ретраи / таймауты / downstream |

## Два потока данных (метрики приложения)

Чтобы ответить «почему медленно», снимать **два потока одновременно**: (1) k6 (RPS / p95 / ошибки) и (2) метрики приложения/системы (CPU, heap, GC, пул, треды). Читать их вместе: k6 говорит *что* медленно, метрики приложения — *что это ограничивает*.

1. **Проверить, отдаёт ли сервис метрики** (Actuator/Prometheus, свой `/metrics`, Grafana) — скил универсальный, не привязываться к конкретному стеку.
2. Если метрик нет — **предложить включить/добавить** (напр. Spring: `management.endpoints.web.exposure.include=prometheus` + гистограмма для `http.server.requests`) и убедиться, что реально получаем: **CPU, heap, GC-паузы, треды, пул соединений (`active`/`pending`/`timeout_total`)**.
3. **Сэмплировать во время прогона** (каждые несколько секунд) и наложить на график k6.

| Сигнал | Диагноз |
|---|---|
| CPU ≈ 100% лимита | compute-bound — профилировать горячие методы |
| пул `active == max` и/или `pending > 0` | pool-bound — очередь за соединением |
| `gc_pause` растёт, частые full GC | GC-bound / тесный heap |
| heap растёт без остановки | утечка |
| треды лезут к максимуму | насыщение worker-пула |

Быстрый первый проход — дерево диагностики:

```
p95 высокий?
├─ CPU > 80%?                    → compute-bound (масштаб / оптимизация)
├─ пул active == max / pending > 0? → pool-bound (пул / оптимизация запросов)
├─ запрос к БД медленный?        → query-bound (индекс / N+1 / кэш)
├─ downstream медленный?         → timeout / circuit breaker
└─ ничего из этого?              → lock/contention → профилировать
```

Паттерны узких мест (сигнатуры → подтверждение → ремедиация, ранжированы от дешёвых к дорогим):
CPU-насыщение, утечка памяти/heap, БД (slow query / N+1 / lock / pool), исчерпание тредов/worker-пула,
сеть/полоса, деградация downstream, cold-start/прогрев, event-loop/async, кэш-шторм (thundering herd).

## Resilience (анализ и улучшения)

Медленный/hanging эндпоинт — обычно **ожидание в очереди, а не CPU**: низкий CPU + высокий p95/p99 = сервис ждёт на очереди, а не считает. Здоровье = контроль очередей ожидания.

Три очереди:
1. **Worker threads** — потоки близки к максимуму → кончились.
2. **Connection pool** — насыщение это `pending` + `timeout_total`, а не `active` (active — мгновенный gauge, на низком трафике 0). Пул = runtime-значение, не дефолт из конфига.
3. **Downstream** — латентность/ошибки/таймауты внешних вызовов.

Рекомендации (только под реальный факт, не выдумывать метрики):
- **Таймауты + timeout получения соединения из пула** — всегда полезны (ограничивают ожидание).
- **Circuit breaker / bulkhead / rate limiter** — только если режим отказа наблюдается (downstream реально медленный/падает); для быстрого downstream «down» уже fast-fail, паттерн лишний.
- **Health-check isolation** — liveness (tcp) отдельно от readiness (http).
- **Observability** — если для диагностики не хватает показателей, предложить их добавить: RED (Rate / Errors / Duration) для запросов и USE (Utilization / Saturation / Errors) для ресурсов. Конкретно: если нет p95/p99 (только `_max`/`_sum`, без `_bucket`) — включить гистограмму (Micrometer `distribution-statistics-histogram`).

Отчёт — единой нитью (BLUF): Резюме → Что измеряли → Результаты → Выводы по severity → Рекомендации → Бизнес-резюме; каждая секция отвечает на следующий вопрос читателя, без повторов. Triage-порядок, паттерны латентности и дерево диагностики — **методология анализа, а не секции отчёта**: их результат вплетается в «Выводы», а не выносится отдельными блоками. SLO и error budget — Google SRE.

**Профилирование — вне скоупа.** Скил снимает baseline (RPS / p95 / ошибки), а не ищет узкое место в CPU / памяти / GC / SQL. Если нужен следующий шаг: для JVM-сервисов — база знаний `jvm-profiling-best-practices.md`, для других стеков — аналог.
