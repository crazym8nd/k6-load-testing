# Генерация seed (SQL-фикстуры)

Правильный путь — **воспроизвести боевую БД**, а не выдумывать данные из головы.

1. **Доступ к БД.** Спросить: можешь сконфигурировать БД и дать данные для подключения (host/port/user/password), или настроить её сейчас? Дальше работаем с боевой БД.
2. **Версия СУБД** (и расширения) — чтобы локальная БД соответствовала.
3. **Диагностический SQL** — генерируем после изучения кода/схемы; собирает по таблицам **в скоупе отобранных эндпоинтов** (не по всем таблицам схемы): число записей (`SELECT 'table' AS tbl, count(*) FROM table UNION ALL ... ORDER BY rows DESC`), связи (FK), примеры уникальных значений.
4. **Наполненность: по умолчанию воспроизводить полные прод-объёмы.** Проверить цифры: если это не «big data» (порядка сотен гигабайт / десятков миллионов строк), локальная БД тянет их без проблем — масштабировать не нужно. Масштабирование вниз — только с явного согласия пользователя: если объёмы реально огромны, спросить «воспроизводить полностью или масштабировать до какого-то значения?» и использовать названное значение, а не дефолтный коэффициент.

Перед генерацией INSERT:
- снять из `information_schema` **unique constraints** (чтобы seed не конфликтовал сам с собой — напр. `attribute.type`, `employee_number.hr_personal_number`);
- **какие таблицы уже засеяны миграциями** (Liquibase/Flyway) — не дублировать (напр. `organizational_structure` уже засижен);
- **изучить enum-коды / бизнес-ключи связей** из кода (константы типа элемента, сервисы/мапперы) — связи критичны: без них запросы падают 404 ещё до бизнес-логики (напр. связка «сотрудник ↔ элемент оргструктуры» через `hr_personal_number ↔ external_id`, код типа элемента `'P'`/`'O'`);
- **понять реальный механизм матчинга** (напр. `getActualPoliciesBySettings`) и генерировать фикстуры под него — не «пустые» записи (политика без настроек матчится всем и маскирует проблему).

Тип `id`: `serial` — вставляй явные id, после `setval` последовательность; `uuid` — генерируй `md5('...')::uuid`.
