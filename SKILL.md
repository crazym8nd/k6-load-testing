# k6 Load Testing

Полный цикл нагрузочного тестирования сервиса через k6 (Docker): сбор данных → конфигурация → smoke → прогон → анализ → сравнение → улучшения.

Скил самодостаточен: k6-инструментарий в `template/scripts` (lib, сценарии, шаблон фикстур). Скопируйте `template/scripts` в целевой каталог и запускайте через `docker run`.

## When to Use

- Померить производительность эндпоинта (RPS / p95 / ошибки) под нагрузкой.
- Найти «колено» (потолок), проверить выживание при всплеске или утечки за часы.
- Появился новый/незнакомый сервис — измерить его производительность.

## Quick Reference

| Тип | Исполнитель | Что даёт | Кто запускает |
|---|---|---|---|
| smoke | constant-arrival-rate | стенд отвечает, фикстуры 200 | агент |
| baseline | constant-arrival-rate | RPS / p95 / ошибки | агент |
| stress | ramping-arrival-rate | «колено» (потолок) | агент |
| spike | ramping-arrival-rate | выживание + восстановление | агент |
| soak | constant-arrival-rate | утечки за часы | **пользователь** |

## Рабочий каталог (scratch)

Все временные артефакты скила — в **одном** каталоге `.tmp/loadtest/` в корне проекта, чтобы потом не искать мусор по проекту:

```
.tmp/loadtest/
├── seed/seed.sql        # SQL-фикстуры (сохранить — чтобы воспроизвести ту же наполненность)
├── scripts/             # скопированный k6-шаблон + endpoints.js + services.js
├── reports/             # отчёты k6 (summary-*.json)
├── docker/Dockerfile    # локальный Dockerfile + app.jar (build-контекст)
└── run.md               # команды запуска стенда и k6 с использованной конфигурацией
```

- Перед созданием — **read-only** проверка, что каталог не попадёт в git: `git check-ignore .tmp/loadtest` (или `git status --porcelain`). Если не игнорируется — **предупредить** пользователя, но ничего не менять.
- **git не трогать** — ни `.gitignore`, ни `git add`/`commit`: управление git вне скоупа скила. Только файлы на диске.
- В конце — удалить `.tmp/loadtest/` (файловая операция), см. шаг 10 «Остановить стенд».
- **Сохранять воспроизводимость**: команду запуска (`docker run` с конфигом) — в `run.md`, а сгенерированный seed-скрипт — в `seed/`, чтобы потом можно было точь-в-точь воспроизвести ту же наполненность и конфигурацию (напр. после улучшений прогнать заново на холодную).

## Флоу

1. **Собрать данные о сервисе** (см. «Сбор данных»).
   > ⛔ **ГЕЙТ.** Не переходить к п.2, пока не закрыты **все** пункты чеклиста «Сбор данных». Каждый пункт закрывается одним из трёх: «узнали сами», «дал пользователь», «не нужно» (только явно). В первую очередь — **«Конфигурация»** (CPU/RAM лимиты, heap `-Xmx`/`MaxRAMPercentage`, пул БД, таймауты) и **«Данные»** (реальные объёмы таблиц в скоупе). Брать произвольные дефолты (`--memory 2g --cpus 2`, мини-seed) **запрещено**.
2. **Поднять стенд.** Разобраться, как запустить сервис в Docker (Dockerfile / готовый jar). Посмотреть, какие образы уже есть (`docker images`). Перед запуском уточнить: «нашли такие-то образы — подойдут для локального, или конкретизировать под прод?» Цель — запуститься максимально близко к прод-условиям. Затем данные: SQL-скриптом или через API.
   > ⛔ **БЛОКЕР.** `docker run` поднимать только с прод-значениями `--memory`/`--cpus`/`-Xmx` и прод-размером пула БД, а seed — под прод-объёмы (по умолчанию **полные**). Значения берутся из kubernetes/deploy-репо или от пользователя, не из головы.
3. **Сконфигурировать k6.** Скопировать `template/scripts` в целевой каталог; создать `scripts/services/<service>/endpoints.js` из шаблона; зарегистрировать в `scripts/lib/services.js`. Фикстуры — из реальных данных, не из головы.
4. **Smoke.** Прогнать `smoke-test.js` — стенд отвечает, фикстуры дают 200. 404/No mapping → не дебажить, взять актуальные маршруты из `/api-docs` работающего сервиса.
5. **Выбрать тип теста.** Четыре типа: **baseline** (постоянная нагрузка: фиксированный `RATE`), **stress** (ступенчатый рост RPS до «колена»), **spike** (внезапный скачок → восстановление) и **soak** (длительная нагрузка; агент не запускает, отдаёт команду пользователю) — детали в `references/test-types.md`. Затем сценарий (`throughput-max` / `get-only` / `post-only`), `RATE`, `DURATION`, `PRE_ALLOCATED_VUS`. VU-sizing: `preAllocatedVUs = ceil(RATE × p95_сек × 1.2)`, а `MAX_VUS` — с запасом (по умолчанию ×40 от preAllocated; при ожидаемом насыщении поднять, иначе k6 молча дропнет итерации — см. «Нагрузка дошла до сервера?»). Per-endpoint SLO: тяжёлые эндпоинты — больше, лёгкие — меньше.
6. **Запустить.** Fail-fast (`k6 archive`) → полный прогон (см. «Запуск»).
7. **Проанализировать отчёт.** По triage-порядку: ошибки → `dropped_iterations` (дошёл ли тест до цели) → p95/p99 vs SLO → тренд по времени → per-endpoint (см. `references/analysis.md`). Ошибка на низкой нагрузке = баг, чинить до выводов о capacity; `dropped_iterations > 0` = нагрузка не дошла, цифры частичны.
8. **Сравнить.** p95 против SLO; между эндпоинтами; с прошлым прогоном (baseline). Превышение SLO → расход error budget (Google SRE). **Regression-пороги против baseline:** p95/p99 регресс > 20% → flag; error rate любой рост → flag; throughput падение > 10% → flag.
9. **Предложить улучшения** — см. `references/analysis.md`.
10. **Остановить стенд.** Остановить всё, что поднимали (сервис, БД, моки): `docker stop`/`docker rm`. Спросить пользователя — удалять ли данные и scratch-каталог `.tmp/loadtest/`.
11. **Выдать отчёт.** Итоговый отчёт (verdict + узкое место + рекомендации) — только **после** остановки стенда.
    > ⛔ **ГЕЙТ.** Не выдавать отчёт, пока стенд не остановлен: сначала остановить поднятые контейнеры, затем финальный отчёт пользователю.

## Сбор данных

Покажи пользователю чеклист входных данных. По каждому пункту он может ответить: «проанализируй сам», дать ссылку на документацию/репо, или текстом.

| Что нужно | Что ищем |
|---|---|
| Эндпоинты | OpenAPI/Swagger или список (path, метод, параметры) |
| Данные | реальные id, объёмы, связи |
| Конфигурация | лимиты, пул БД, таймауты — из деплой-репо или kubernetes |
| Зависимости | внешние REST API |
| Стенд | поднять локально в Docker (БД + сервис), `BASE_URL` |
| Метрики/логи | дашборд Grafana / MCP-доступ (p95/p99, ошибки, насыщение пулов) |
| Ожидаемая нагрузка | пик RPS/пользователей — из Grafana/прод-метрик или от пользователя (для стресса: вокруг какой цифры искать «колено») |

Как собрать:

1. **Найти исходники.** Взять OpenAPI/Swagger, затем найти код. Проверить рабочую директорию, откуда вызван скил. Нет кода — спросить ссылку на репозиторий (удалённую или локальный путь). Убедиться, что ссылка ведёт на нужный сервис. Маршруты брать из **работающего** сервиса (`/api-docs` или `/swagger-ui`), а не из спеки в репо — она может устареть.
2. **Отобрать эндпоинты.** Все из спеки; если много — по коду найти связанные с БД или тяжёлые (агрегации, пакетные, обращения к downstream). При выборе обращать внимание на **lazy-коллекции / `@OneToMany` / open-in-view** — частый источник N+1, всплывающий только под нагрузкой (в фикстуру взять и «широкий» узел — много детей, и лист). Предложить. Спросить: «эти», «все», или пользователь даст свой список. Спросить про метрики/логи и ссылку на дашборд (Grafana); если есть MCP-доступ — снять p95/p99, ошибки, насыщение пулов по эндпоинтам.
3. **Генерация данных.** По коду разобраться, откуда данные: SQL-скрипт или через API. Дать пользователю выбор.
4. **Данные** — схема из миграций (Liquibase/Flyway), объёмы из прод-метрик. **Скоуп = только таблицы, которые читают отобранные эндпоинты** (определять по entity/сервису/мапперу контроллера), а не все таблицы схемы. Связь критична: без связи запросы падают ещё до зависимости (404).
5. **Конфиг** — сначала выписать, **какие значения нужны** (CPU limit/request, RAM, heap `-Xmx`/`MaxRAMPercentage`, пул БД, таймауты соединения), затем **попытаться их найти** (деплой-репо / Helm `values.yaml` / `kubectl -n <ns> get deployment <service> -o yaml` — что доступно). Если часть не нашлась — **отчитаться**: «нашли A, B, C; не нашли X, Y — дай значения или скажи, где взять (деплой-репо / доступ в kubectl)». Сюда же спросить: **отключать ли авторизацию** (если это возможно env-флагом / security-конфигом) — для чистого замера читающих эндпоинтов или оставить как в проде.
6. **Зависимости** — внешние REST API, которые надо замокать (см. WireMock ниже).

## Запуск (docker)

Сначала создать каталог отчёта — без него `summary.json` не сохранится, k6 упадёт в конце прогона с `no such file or directory`:

```bash
mkdir -p reports
```

```bash
docker run --rm -u "$(id -u):$(id -g)" -v "$PWD":/k6 -w /k6 \
  grafana/k6:0.57.0 run -e SERVICE=<service> -e BASE_URL=<url> scripts/<scenario>.js
```

`<scenario>`: `smoke-test` | `throughput-max` | `throughput-get-only` | `throughput-post-only` | `throughput-stress` | `throughput-spike` | `throughput-soak`.

Env (дефолты в `config.js`): `RATE`=5, `DURATION`=2m, `PRE_ALLOCATED_VUS`=10, `MAX_VUS`=preAllocated×40, `GRACEFUL_STOP`=30s, `SLO_P95_MS`=500. Переопределить — добавить `-e RATE=20 -e DURATION=5m -e MAX_VUS=2000`.

Fail-fast перед полным прогоном:

```bash
docker run --rm -v "$PWD":/k6 -w /k6 \
  grafana/k6:0.57.0 archive -e SERVICE=<service> -O /tmp/k6-check.tar scripts/<scenario>.js
```

`-e` — флаг k6 (после `run`/`archive`), а не docker `-e`: docker `-e` задаёт env контейнера, который `k6 archive` не видит в `__ENV`.

`-u "$(id -u):$(id -g)"` — чтобы `reports/` писался от текущего пользователя (каталог должен существовать — см. `mkdir -p reports` выше).

**Два замера: холодный → горячий.** Сначала прогнать на холодную (сразу после старта стенда), затем на горячую (после прогрева) — так будут данные и до прогрева, и после. Холодный прогон показывает cold-start (JIT / Hibernate / кэши Postgres пустые), горячий — установившееся поведение. Не замерять только одну точку: cold vs warm различаются в разы.

**Cold-start — не «мусор», а аргумент с весом в трёх местах:**
1. **«Эндпоинт медленный» по холодному замеру** — это warm-up, а не деградация: оценивать по steady-state (горячему), холодный не смешивать с насыщением. Пример: холодный p95≈2с — это warm-up, а не насыщение (steady-state 17мс).
2. **Autoscaling / readiness** — новый инстанс стартует холодным, первые запросы тормозят: нужен прогрев (низкий трафик перед приёмом боевого) или readiness-гейт, не пускающий трафик до прогрева.
3. **Короткий прогон (< 5 мин)** — холодное окно попадает в агрегат и завышает p95: первые 2–5 мин исключать из оценки SLO.

## Нагрузка дошла до сервера? (dropped_iterations + check)

`constant-arrival-rate` при нехватке VU **молча дропает** итерации — они не попадают в
`http_req_failed`, поэтому «0% ошибок» при высоком RPS может означать «k6 не смог влить
нагрузку», а не «сервер выдержал».

- **`dropped_iterations`** — главный сигнал. `> 0` → цель по RPS превысила пропускную
  способность сервера (или занижен `MAX_VUS`). Сначала поднять `MAX_VUS` и перегнать; только
  если дропы остались — это насыщение сервера.
- **`preAllocatedVUs = ceil(RATE × p95_сек × 1.2)`** — стартовый пул VU; `MAX_VUS` — с запасом
  (при насыщении p95 растёт → VU нужно больше, чем даёт формула).
- **Три механизма проверки:** `check()` — per-запрос диагностика (не валит тест); `threshold` —
  агрегатный SLA-гейт (валит тест, exit 99); `fail()` — рвёт текущую итерацию.
- **`GRACEFUL_STOP ≥ 2 × p99`** — чтобы хвост не обрезался и не дал ложных ошибок.
- **`abortOnFail`** на пороге p95 — ранний аборт при breach. **Не включать** на baseline/холодном замере — нужны полные данные за весь прогон, включая cold-start. **Включать**, когда цель — «щупать» предел (поиск точки насыщения): после breach картина уже ясна, гонять дальше незачем.

Интерпретация пары:

| `dropped_iterations` | `http_req_failed` | Вывод |
|---|---|---|
| 0 | 0% | сервер тянет target rate |
| > 0 | 0% | сервер НЕ тянет target rate — очередь растёт, мягкая деградация (замедление, не ошибки) |
| 0 | > 0% | сервер отвечает, но с ошибками (баг или отказ downstream) |

Заниженный `MAX_VUS` также искажает латентность насыщения: очередь ограничена числом VU,
поэтому p95 получается **меньше** реального (пример: p95=1.3с при maxVUs=300 против 7с при
maxVUs=2400 на том же RATE=500).

## Частые ошибки

- Фикстуры отсутствуют в данных стенда → 404; брать id из реального seed.
- Один SLO на все эндпоинты → тяжёлый эндпоинт валит тест; задавать per-endpoint `sloP95Ms`.
- Пропустить smoke → полный прогон падает на нерабочих фикстурах.
- Не учесть downstream-зависимости → 429/502 искажают картину (это не баг самого сервиса).
- Не смотреть `http_req_waiting`/`http_req_blocked` → путать сетевую задержку с медленным сервером.
- Не мониторить `dropped_iterations` → «0% ошибок» при дропах = «k6 не влил нагрузку», а не «сервер выдержал»; заниженный `MAX_VUS` занижает p95 насыщения.
- Запустить стенд/прогон на произвольном конфиге (CPU/RAM/пул) и мини-данных вместо прод-значений → тест показывает насыщение локального дефолта, а не реальное поведение сервиса. Сначала закрыть «Конфигурацию» и «Данные» из чеклиста.
- Не прогреть стенд → первый прогон даёт завышенные p95 (cold vs warm, JIT + кэши); замерять только после прогрева.
- «Пустая» фикстура / мини-seed вместо реального механизма матчинга → маскирует проблему (напр. политика без настроек матчится всем).
- Не проверить, отдаёт ли сервис метрики (Actuator/Prometheus) → нечем объяснить «почему медленно»; предложить включить метрики заранее.
- Разбросать артефакты по проекту → мусор; всё складывать в `.tmp/loadtest/`.
